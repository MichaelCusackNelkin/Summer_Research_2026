live/ — daily orchestrator and retrain

Operator’s guide. Everything here runs from the repo root through the project virtualenv (.venv/bin/python). Repo conventions (paths, DATABENTO_API_KEY spelling, active universe) live in ../CLAUDE.md — read that once, then this.

1. What this is

The research pipeline in this repo estimates three pieces — a return forecast (forecast/forecasting.ipynb), a factor covariance matrix (covariance/covariance.ipynb), and a square-root market-impact model (impact/impact_estimation.ipynb) — and solves them together as a daily mean-variance optimization (optimizer/optimal_portfolio.ipynb). Those notebooks are the authoritative research references; this directory is the production port of the same math.

live/ contains three scripts. live/daily_orchestrator.py runs once per trading day: it streams Databento imbalance + tbbo from market open, snapshots at 15:50 America/New_York, engineers the same features the forecast pipeline was trained on, predicts alpha, solves the MVO, converts dollar targets to signed share counts, and executes them as a two-leg batch — MKT entries at 15:50 sized to target - current, then MOC counter-flatten sized to the ACTUAL post-entry position — so the book is flat overnight and the run captures the forecasted 15:50→16:00 close-auction move. live/retrain.py runs on a slower cadence (weekly or monthly), refreshes the historical Databento cache on a rolling window, and rebuilds the three artifact sets on disk. live/panic.py is the account-wide kill switch (see section 10). The daily reads whatever the retrain last wrote; there is no other coupling between them.

2. Prerequisites

Install

.venv/bin/pip install -e ./data_collection
.venv/bin/pip install -e ./ibkr_broker

Environment

  • DATABENTO_API_KEY in .env at the repo root. The legacy hyphenated DATABENTO-API-KEY spelling is also accepted for compatibility with the notebooks — the underscore form is preferred.
  • Interactive Brokers TWS (or IB Gateway) running with API access enabled. See ibkr_broker/src/ibkr_broker/broker.py for the port layout (7497 paper, 7496 live, 4002/4001 for Gateway) and TWS API setup notes. The daily orchestrator refuses paper-mode connections to a live port and refuses live-mode without the confirmation string.

Artifacts required before the first run

The daily orchestrator fails fast if any of these are missing:

If you have never run retrain.py, the safe path is to first run the three research notebooks end to end to seed the artifact directories, then let retrain.py take over on the recurring schedule.

3. Testing without a live Databento subscription

Paper trading with Interactive Brokers and market data from Databento are independent subscriptions. The live imbalance schema in particular is expensive (order of $1000s/mo); you can validate almost the entire pipeline before turning it on. In order of increasing cost and realism:

Layer 0 — the test suite (cost: 0)

.venv/bin/python -m pytest data_collection/tests/ live/tests/ -v

Proves feature engineering matches the offline notebooks, the MVO solve produces a valid book against real on-disk covariance, the symbol-mapping logic handles Databento’s live gateway convention, the atomic-write helpers do not corrupt artifacts, the coverage / empty-book / unqualified-symbol / oversized-leg guards fire, and the replay + broker-connect exit paths return coded rcs. Runs in under two seconds.

Layer 1 — replay mode against cached historical data (cost: 0 beyond already-cached history)

.venv/bin/python -m live.daily_orchestrator --replay-date 2026-05-15 --paper

Replay sources imbalance + tbbo from the historical parquet cache the retrain / notebooks already populated, feeds them through the SAME _build_live_day_frame -> alpha -> MVO -> sizing -> pre-qualify -> MOC path a real run uses, and (by default) stops one step short of order submission. The only thing NOT exercised is the live websocket transport — everything downstream is identical to a real session.

First replay of a date not in the cache would need a one-off Databento historical materialisation (not the paid live subscription — cheap historical). By default the cache-aware fetch guard refuses that fetch and raises CoverageError naming the closest cached parquet and the shortfall, so a cold-cache rehearsal cannot silently rack up a batch charge. Pass --allow-fetch to authorise it (replay only — see the “Cache-aware fetch guard” section below for the full picture).

--replay-submit opts in to placing real paper MOC orders — see section 4 for the full flag reference, including the guard matrix and the caveats.

The cache guardrail and the universe drift trap

Both daily_orchestrator --replay-date and retrain route every historical read through the coverage manifest (see live/cache.py). The default is --allow-fetch OFF: if the requested {schema, [start, end), symbols} slice is not covered by an existing parquet the resolver refuses to submit a Databento Batch API job and raises a self-diagnostic CoverageError naming the nearest parquet and the shortfall (days at head/tail, or count of missing required symbols). This is what stops a stale --end-date or a drifted universe file from quietly paying for a fresh fetch.

Two gates guard a real fetch:

  • retrain: --allow-fetch AND --yes (interactive yes on a TTY is accepted in place of --yes). Both required because batch API calls cost real money.
  • daily_orchestrator --replay-date: --allow-fetch alone (single gate — replay is a one-day historical pull, cheap).

New retrain exit codes when the gates trip:

  • 9 — coverage MISS and --allow-fetch not set; nothing fetched.
  • 10 — --allow-fetch set but confirmation refused (no --yes, no TTY, no at the prompt, or Ctrl-D). Nothing fetched.

The universe drift trap. retrain --refit forecast|impact|all reads imbalance, tbbo, and statistics for the broad universe (--broad-universe-file, default universe.txt), not just the active set. The parquet cache is keyed on the exact ticker list — so if the broad universe file has been rebuilt since the cache parquets were materialised, retrain will MISS even for a small active universe. Concrete example: top_50_universe.txt today includes CRWV; the cached tbbo parquet from an earlier notebook run does not. A retrain --refit impact --broad-universe-file top_50_universe.txt run against that cache MISSes with:

coverage plan — tbbo: MISS (nearest 6436dd54a7ced32262a3242e08d42d20.parquet: parquet missing 1 required symbol(s), e.g. ['CRWV'], shortfall=1)

Two ways out:

  1. Match the broad file to what the cache was built for — e.g. pass --broad-universe-file universe.txt (the fully-cached pool) even when the active file is smaller. The coverage-HIT filter pares the result down to the active set on the fly.
  2. Pay the delta: --allow-fetch --yes submits a fresh batch job for the missing symbols.

The near-miss log names the closest parquet and the shortfall so an operator can diagnose without hand-inspecting the parquet cache. Sample outputs:

# HIT — schema and range and symbols all present
coverage plan — tbbo: HIT (015b0f098e17be916bbb238312a4d5d4.parquet)

# MISS on missing symbol
coverage plan — tbbo: MISS (nearest 6436dd54a7ced32262a3242e08d42d20.parquet: parquet missing 1 required symbol(s), e.g. ['CRWV'], shortfall=1)

# MISS on short at tail
coverage plan — imbalance: MISS (nearest 015b0f098e17be916bbb238312a4d5d4.parquet: parquet ends 2026-06-10, request needs 2026-06-30 (short 20d at tail), shortfall=20)

Layer 2 — cheap live-transport smoke

The live tbbo / mbp-1 schemas are far cheaper than live imbalance. Since LiveFeed’s connect / reconnect / symbol-mapping code path is schema-agnostic (imbalance and tbbo take the same route), a tbbo-only session over LiveFeed validates the transport in production. Do this once before committing to the live imbalance subscription; it catches auth, network, and symbology issues without paying for close-imbalance data.

Layer 3 — the real thing, paper first

Once layers 0-2 pass:

  1. Buy the live imbalance subscription.
  2. Run .venv/bin/python -m live.daily_orchestrator --paper --dry-run for a few sessions. Confirm the log shows a well-formed target book (non-empty, sensible GMV, coverage above the threshold) and no errors.
  3. Drop --dry-run for --paper — real paper MOC orders. Compare the next morning’s broker.reconcile_positions warnings against the persisted target JSON.
  4. Only after several clean paper sessions, run --live with the confirmation string.

4. The daily orchestrator

.venv/bin/python -m live.daily_orchestrator --help

CLI reference

Mode:

  • --paper — paper mode. Default. Connects to TWS port 7497.
  • --live — live mode. Requires --live-confirm=YES_I_WANT_LIVE_TRADING and connects to port 7496. Mutually exclusive with --paper.
  • --live-confirm LIVE_CONFIRM — broker confirmation string required with --live. Must be exactly YES_I_WANT_LIVE_TRADING (defined at Broker.LIVE_CONFIRM_MSG).
  • --dry-run — compute alpha, solve MVO, log the intended book, do not connect to the broker and do not place any orders.

Replay (dress-rehearsal):

  • --replay-date YYYY-MM-DD — instead of the live gateway, source imbalance + tbbo from the cached historical adapter for the given trading day (America/New_York). Skips the stream-start and snapshot wall-clock waits and bypasses the --submit-by cutoff — the wall clock is unrelated to the historical date. First replay of an un-cached date may trigger a one-off Databento historical materialisation (cheap historical, not the paid live subscription). Default: unset.
  • --replay-submit — opt in to placing REAL paper MOC orders during a replay run. Off by default; without it, replay is broker-free (computes, logs, persists the book, exits before touching TWS). Only valid with --replay-date. Always paper — combining with --live is refused regardless.
  • --allow-fetch — authorise the replay feed to submit a Databento Batch API job when the local cache cannot cover the requested day. Off by default; a cold-cache replay refuses rather than silently paying for a fresh historical materialisation. Only meaningful with --replay-date; ignored on the live path (no historical cache in the loop). Single gate — replay is a one-day historical pull, so no --yes co-gate.

The replay guard matrix, stated plainly:

  • --replay-date + --live → refused, rc=6. Replay can never touch a live account.
  • --replay-submit without --replay-date → refused, rc=7. The broker path is untouched.
  • --replay-submit with a live --broker-port (7496 / 4001) → the broker’s own live-port guard trips at connect time, returning rc=8. Paper-only, always.

Replay date range: anything inside 2025-06-11..2026-06-10 for the currently cached parquets. Use a weekday — Wednesdays are the safest default (no exchange-holiday adjacency); 2026-05-13 is a good picked-at-random rehearsal date. Weekend dates trigger a MISS on the manifest since no bars exist for them.

Reference-stats prerequisite: impact/reference_stats.parquet MUST exist before any replay, or the C2 coverage assertion aborts the run at 0% and returns rc=2. Generate it via retrain --refit impact (see section 6). Explicit ordering:

# Step 1 — populate impact/reference_stats.parquet.
.venv/bin/python -m live.retrain --refit impact --end-date 2026-06-11
# Step 2 — now replay is safe.
.venv/bin/python -m live.daily_orchestrator --replay-date 2026-05-13 --paper

Replay caveats:

  1. --replay-submit paper fills happen at TODAY’s close, not the historical date’s close, so PnL is not realistic. Replay validates plumbing, not PnL. The startup log emits a loud WARNING every time --replay-submit is used.
  2. Baseline pollution. --replay-submit paper fills sit in the TWS paper account and pollute the next real run’s diff baseline: broker.get_positions() on the following day will look like drift and the strategy will trade to unwind them. Flatten the paper account between rehearsals — python -m live.panic --paper (see section 10). Also do this before switching from --replay-submit back to a real paper session.
  3. Replay ADV / vol come from the retrain-time reference-stats snapshot, which is likely as-of a date AFTER the replayed historical date. That is mild look-ahead in the impact and cost denominators. This is intentional (replay parity with the live code path), not accuracy.
  4. Replay target books are quarantined in live/logs/targets/replay/ and never enter next-day reconciliation.

Sizing:

  • --vol-cap VOL_CAP — target daily dollar-volatility cap. Default
    1. The QP is scale-invariant — this is the effective risk limit.
  • --lambda- LAM — risk aversion per dollar. Default 5e-05. Must be positive; <= 0 returns rc=9. The optimizer’s scale is auto-computed as 1 / lambda (see “Lambda auto-scale” below).
  • --impact-gamma IMPACT_GAMMA — scalar impact gamma used when no per-name vector is loaded. Default 0.5.
  • --use-impact-vector — load impact/impact_gamma_vec.npy and use per name (default on).
  • --no-impact-vector — disable per-name impact gamma; use the scalar.

Lambda auto-scale. The QP is scale-invariant; scale is a numerical conditioning hint, not a book-sizing knob. The unconstrained optimal book is approximately y* ≈ Σ⁻¹α / λ, so 1/λ is the natural order of magnitude — the code auto-sets scale = 1 / args.lam. The actual GMV a run produces comes from --vol-cap, --lambda-, and the impact + cost terms; there is no dedicated GMV knob. (The old --target-gmv flag was misleadingly named — read as a sizing knob but only touched scale — and has been removed.)

Timing (all America/New_York):

  • --stream-start-time STREAM_START_TIME — time to open the live feed. Default 09:30. See section 5 for the timing gotchas.
  • --rebalance-time REBALANCE_TIME — time the snapshot clock is anchored to. Default 15:50.
  • --print-wait-secs PRINT_WAIT_SECS — seconds after --rebalance-time to wait before snapshotting the buffers. Default 10. The imbalance print publishes at 15:50:00+, so a 0s wait races it.
  • --submit-by SUBMIT_BY — hard cutoff (HH:MM ET) for MOC EXIT submission. Default 15:55. Note: the NYSE/Nasdaq MOC entry cutoff is 15:50 ET, so any leg placed after 15:50 may face exchange rejection. This flag ONLY bounds the MOC exit batch; the MKT entry batch fires unconditionally so the operator is never left with a filled entry and no queued exit. If the cutoff was already past at orchestrator entry (no orders placed), the run exits rc=4 (safe skip). If it trips mid-flow AFTER entries filled, the run exits rc=11 (OVERNIGHT EXPOSURE — page).

Execution (two-leg — see the “Execution model” section below):

  • --moc-ack-timeout MOC_ACK_TIMEOUT — bounded wall-clock (seconds) the MOC acceptance audit waits per-oid for a terminal state after the MOC batch is sent. An MOC that reaches Cancelled / ApiCancelled / Inactive with filled=0 within this window is treated as REJECTED at the exchange and escalates the run to rc=11. TimeoutError (still Submitted at deadline) is presumed accepted; MOCs sit Submitted until 16:00 and fill there. Default 60. Trade- off: shorter = faster operator feedback but risks false rc=0 if a rejection propagates later than the window (rare; rejections are typically terminal within seconds). Longer = more reliable rejection detection but adds up to that many seconds to every happy run’s wall clock. Late rejections beyond the window are caught next morning by broker.reconcile_positions at startup.

Safety and data quality:

  • --on-feed-failure {abort,proceed} — action if the live feed is stale, never connected, or fails the coverage check. Default abort. Note: a feed-start failure (adapter raises out of LiveFeed.start() / ReplayFeed.start()) always returns rc=2 regardless of this flag. That is strictly safer — a dead feed produces an empty book downstream anyway, and rc=2 makes the exit honest.
  • --min-universe-coverage MIN_UNIVERSE_COVERAGE — minimum fraction of the active universe that must appear in the snapshot for the run to proceed. Default 0.5.

Configuration:

  • --universe-file UNIVERSE_FILE — active-universe filename at the repo root. Default top_100_universe.txt.
  • --reference-stats-path REFERENCE_STATS_PATH — override for the reference-stats parquet. Default impact/reference_stats.parquet.
  • --no-live-feed — skip the Databento live feed entirely. Only useful with --dry-run for smoke tests; alpha will be zero everywhere.

Broker:

  • --broker-host BROKER_HOST — TWS host. Default 127.0.0.1.
  • --broker-port BROKER_PORT — TWS port. Default auto (7497 paper, 7496 live).
  • --broker-client-id BROKER_CLIENT_ID — TWS client id. Default 1. Use distinct ids per running process.

Recommended production sequence

Progressive bring-up — each step validates a strictly larger surface than the one before it. Do not skip:

# 1. Confirm cache HITs without touching the network or writing artifacts.
.venv/bin/python -m live.retrain --refit impact --dry-run

# 2. Actually generate impact/reference_stats.parquet (and the impact
#    vector) — needed for any replay to survive the coverage assertion.
.venv/bin/python -m live.retrain --refit impact

# 3. Broker-free rehearsal against cached historical data. Validates
#    feed -> features -> alpha -> MVO -> sizing -> pre-qualify without
#    touching TWS. Pick any weekday inside your cached window; a
#    Wednesday avoids exchange-holiday adjacency.
.venv/bin/python -m live.daily_orchestrator --replay-date 2026-05-13 --paper

# 4. Real paper broker: MKT entries + MOC exits through the paper
#    account. Flatten the paper account (`panic --paper`) before the
#    next real session — replay fills pollute the diff baseline.
.venv/bin/python -m live.daily_orchestrator \
  --replay-date 2026-05-13 --paper --replay-submit

# 5. Live feed, paper broker — the last step before real money.
#    Run for several sessions and eyeball the target-book / fills logs.
.venv/bin/python -m live.daily_orchestrator --paper

# 6. Live feed, live broker. Real money.
.venv/bin/python -m live.daily_orchestrator \
  --live --live-confirm YES_I_WANT_LIVE_TRADING

# If anything goes wrong at any step, the kill switch:
.venv/bin/python -m live.panic --paper --flatten-with MKT
# (or the --live variant with --live-confirm=... --yes)

Safety guarantees

  • Default mode is --paper. Live mode requires both --live and the exact confirmation string; the broker refuses paper-mode connections against a live port.
  • --dry-run short-circuits before any broker connection.
  • Replay is broker-free by default; --replay-submit is the only path from a replay run into the paper broker.
  • Coverage assertion in _build_live_day_frame raises before any broker connect if the live snapshot covers less than --min-universe-coverage of the universe. Combined with --on-feed-failure abort (default), the orchestrator exits with rc=2.
  • --lambda- <= 0 returns rc=9 without contacting the broker. Kept below the rc >= 11 pager threshold — invalid args are a safe skip, not an exposure.
  • An empty share_targets after alpha/MVO returns rc=5 without connecting to the broker. This prevents an all-zero book from flattening every existing position.
  • Out-of-universe positions are pinned to their current quantity in the extended target so they diff-out to zero — the strategy never touches a position it did not put on. Both MKT entries and MOC exits respect this.
  • Every symbol is pre-qualified through TWS before the per-leg loop. Symbols IB refuses to qualify are dropped from the target with a warning; the batch continues.
  • Legs whose absolute diff would exceed Broker.MAX_ORDER_QTY (default 10,000) cause the ceiling to be raised for this session, with the computed new value logged. Nothing crashes on an oversized leg.
  • Structural safety invariant of the two-leg model. The MOC exit quantity is derived from broker.get_positions() AFTER the entry fills settle, NEVER from target - current or the entry’s requested quantity. A partial MKT fill therefore cannot cause an over-flatten into an opposite overnight exposure. Enforced by _submit_moc_flatten not accepting any target-side argument in its signature.
  • Ground-truth coverage cross-check. After the MOC batch, an independent per-symbol check re-polls each entry’s true fill via broker.get_order_status, computes expected_held + moc_signed, and any symbol with non-zero remainder escalates to rc=11. Closes partial get_positions() snapshots, budget-exhausted fill-waits where the poll-derived filled_qty=0 hides real fills, and TWS event-stream brownouts where get_order_status returns stale non-terminal reads (all treated as pessimistic full fill).
  • MOC exchange-acceptance audit. TWS’s placeOrder returns the oid synchronously BEFORE any exchange ack. An MOC submitted past the ~15:50 exchange cutoff is API-accepted then Cancelled at the exchange. _audit_moc_acceptance waits up to --moc-ack-timeout seconds per-oid for terminal state; any MOC reaching Cancelled / ApiCancelled / Inactive with filled=0 escalates to rc=11.
  • The per-leg MOC submit re-checks the wall clock against --submit-by before each order — legs that would land past the cutoff are skipped, not silently rejected by TWS. Replay mode neutralises this cutoff (the wall clock is unrelated to the historical date).
  • Broker-connect failures (live-port guard tripping, TWS down, bad client_id) return rc=8 rather than a bare traceback. No orders were placed at that point.
  • Tail I/O failures cannot downgrade an rc=11 exposure verdict. Target-book persist and the JSONL fill audit are best-effort with try/except logger.exception(...). The exposure decision is computed from all in-memory signals BEFORE any disk I/O; a disk-full raise on the amended target record does not propagate to main() and does not drop rc=11 to rc=1.

Exit codes

Pager predicate: rc >= 11 is the ONLY code that implies a live book at close. Every other code in [2, 10] is a safe pre-order refusal or a clean shutdown. Wire the pager to page on rc >= 11 and to log (don’t page) on any other non-zero.

  • 0 — MVO solved and orders (or dry-run / broker-free replay summary) completed. For a --paper or --live run, both legs fired, the coverage cross-check found no gaps, and the MOC acceptance audit found no exchange rejections.
  • 2 — live feed / feature build failed. Includes the coverage assertion (a thin snapshot) AND any exception out of LiveFeed.start() / ReplayFeed.start() (e.g. cold-cache replay of a weekend, adapter auth error). rc=2 fires regardless of --on-feed-failure for a feed-start exception — strictly safer.
  • 3 — MVO solver returned a non-optimal status.
  • 4 — clock is past --submit-by at the moment the orchestrator was about to submit; nothing was placed. Never fires in replay mode. Distinct from rc=11 — rc=4 is a SAFE PRE-ORDER SKIP.
  • 5 — target book was empty and --dry-run was not set. The broker was not contacted.
  • 6 — --replay-date + --live was requested. Refused. No broker contact.
  • 7 — --replay-submit was requested without --replay-date. No broker contact.
  • 8 — the broker refused the connection. Most commonly the live-port guard on a paper-port mismatch, TWS not running on the expected port, or a --broker-client-id collision.
  • 9 — --lambda- <= 0 (invalid argument). No broker contact. Below the pager threshold — this is a validation failure, not an exposure.
  • 11 — OVERNIGHT EXPOSURE POSSIBLE — page the operator. Entries filled but the MOC exit could not fully cover the book. Fires on any of: MOC legs skipped past --submit-by mid-flow, get_positions raised during the MOC snapshot, the snapshot came back stale-empty after fills, the coverage cross-check found uncovered symbols (partial snapshot / budget-exhausted-with-real-fill / TWS-brownout stale non-terminal get_order_status), or the MOC acceptance audit found exchange rejections (MOC placed after ~15:50 cutoff). The ERROR log line includes the concrete panic command and the uncovered / rejected symbols to name.

Execution model — two-leg

The strategy is intraday, not overnight. The forecast predicts the 15:50→16:00 close-auction return. To capture that PnL the live path enters at 15:50 and exits at the 16:00 close, so the book is FLAT overnight. Each trading day is independent.

Execution is two batches, in strict sequence, per name in the target book:

LEG 1 — MKT entries. For each name where diff = target_shares - current_shares != 0, broker.buy(sym, qty, order_type="MKT") / broker.sell(sym, qty, order_type="MKT") submits a plain market order at the broker default tif="DAY". The bounded per-order fill-wait (default 5s per order, capped by a global deadline tied to --submit-by - 30s) gathers terminal states. Any entry still non-terminal at the wait’s end gets an explicit broker.cancel(oid) — this is the sole mechanism preventing a stuck entry from lingering past the MOC snapshot and causing a late naked fill.

Why plain MKT and not a slippage-capped LMT? Earlier designs tried an IOC LMT capped at a max-slippage-bps from the entry mid, then a plain MKT-IOC. Both were simplified out per operator preference: a slippage cap that binds during the 15:50 pre-close is more likely to leave an unhedged position than to save meaningful basis points, and the strategy’s alpha is more sensitive to fill rate than to entry price. Plain MKT gives the book the best chance of being filled and, therefore, of being hedged by the MOC leg. Slippage on the entry is priced into the impact and cost terms of the QP objective.

LEG 2 — MOC counter-flatten. broker.get_positions() is called FRESH after the entry batch settles. For every managed-universe symbol with a non-zero net position, a per-symbol MOC is submitted in the OPPOSITE direction sized to abs(current_qty). Out-of-universe positions are ignored (never touched).

The core safety invariant. The MOC exit quantity is drawn from the freshly snapshotted position book, NEVER from target - current or from the entry’s requested quantity. A partial MKT fill (say 50%) therefore produces a 50% MOC counter, and the book returns to zero. A target-diff MOC would over-flatten a partial into an opposite overnight exposure — the exact bug this two-leg model exists to prevent. Structurally enforced: _submit_moc_flatten’s signature does not accept any target-side argument.

Coverage cross-check. After the MOC batch is submitted, an independent per-symbol check re-polls each entry’s TRUE fill via broker.get_order_status(oid), computes expected_held = current_baseline + Σ signed_fills, and any symbol with expected_held + moc_signed_by_sym != 0 is flagged as uncovered → rc=11. This closes:

  • Partial get_positions() snapshots — TWS reconnect returns 3 of 10 held names; the missing 7 would ride unhedged.
  • Wait-budget-exhausted — _wait_entry_fills hits its global deadline and marks filled_qty=0 for the remainder, but the MKTs may truly have filled at the exchange. The cross-check re-polls ground-truth.
  • TWS event-stream brownout — get_order_status returns successfully with a stale non-terminal status. The cross-check treats non-terminal-at-cross-check-time as a staleness signal and assumes pessimistic full fill (overcounting exposure > silently missing it).

MOC exchange-acceptance audit. broker.buy/sell returns the oid the moment TWS API-accepts placeOrder — BEFORE any exchange ack. An MOC submitted past the ~15:50 exchange entry cutoff (a not-uncommon outcome on a slow-TWS day where the MOC batch fires 15:50:20+) is API-accepted, an oid comes back, but the exchange REJECTS it and the order becomes terminal Cancelled with filled=0 within seconds to a minute. _audit_moc_acceptance waits up to --moc-ack-timeout (default 60s) per-oid for a terminal state; any MOC reaching Cancelled / ApiCancelled / Inactive with filled=0 is treated as REJECTED → rc=11. A TimeoutError (still Submitted at the deadline) is presumed accepted; MOCs sit Submitted until 16:00.

Trade-off. A stricter default would be to block on real fill confirmation until 16:00 (~8 minutes of wall-clock for a 15:52 run) — that catches an MOC that was accepted at ack then Cancelled minutes later. The 60s default trades that small residual for faster operator feedback. Late rejections beyond the window are caught next morning by broker.reconcile_positions at startup (the drift warning is loud). Widen --moc-ack-timeout on chronically slow venues.

Tail I/O is best-effort. The rc=11 verdict is computed from all in-memory exposure signals (moc_skipped, moc_positions_unknown, empty_snapshot_after_fills, uncovered_symbols, unfilled_moc_syms) BEFORE any disk write. _write_target_record and the JSONL fill audit both run inside try/except logger.exception(...). A disk-full raise on the amended target record does not propagate to main() and does not drop the exposure verdict from rc=11 to bare-exception rc=1.

5. Timing gotchas

The out-of-the-box --stream-start-time 09:30 default is convenient if you already have a systemd unit or a shell that fires at market open, but you do not have to keep the feed alive for six hours.

  • --stream-start-time only gates the feed when you launch EARLY. If you launch after that time, the feed starts IMMEDIATELY on launch. So the flag is a floor, not a schedule.
  • The real timing constraint is the 15:40 feature floor. recent_return uses the 15:40:00-15:49:59 mid-price window, so the buffer must be capturing tbbo by 15:40. Launching “a few minutes before 15:50” is TOO LATE — the recent_return cross-section will silently truncate to only the last minute or two of the window and the alpha will skew. There is no error for this; the day_df will build with a short window and the coverage assertion will not necessarily catch it.
  • Practical schedule: launch by ~15:37 ET so the Live client has headroom to connect, subscribe, and receive the first tbbo tick before 15:40. Set --stream-start-time 15:35 (the effective floor) and schedule the process to fire a minute before that.
  • ADV / vol come from reference_stats (retrain-produced), NOT from the intraday buffer. The buffer only needs data from 15:40 onward. This is why a 15-minute pre-close window is enough — you are not reconstructing daily statistics on the fly.

A cron-style schedule that minimises live-imbalance airtime:

34 15 * * 1-5   .venv/bin/python -m live.daily_orchestrator --paper --stream-start-time 15:35

6. The retrain script

.venv/bin/python -m live.retrain --help

CLI reference

  • --refit {all,covariance,forecast,impact} — which artifact set to rebuild. Default all.
  • --window-months WINDOW_MONTHS — rolling window in months for the forecast and impact fits. Default 12.
  • --covariance-window-days COVARIANCE_WINDOW_DAYS — days of daily bars for the covariance fit. Default 730 (about 24 months).
  • --end-date END_DATE — explicit end date, YYYY-MM-DD, exclusive per Databento’s convention. Default yesterday.
  • --n-factors N_FACTORS — number of SVD factors for the covariance. Default 10.
  • --broad-universe-file BROAD_UNIVERSE_FILE — broad-universe file used for the Databento historical scan. Default universe.txt.
  • --active-universe-file ACTIVE_UNIVERSE_FILE — active universe used to align the saved vectors. Default top_100_universe.txt.
  • --forecast-alpha FORECAST_ALPHA — Lasso regularization strength for the forecast fit. Default 1e-4.
  • --dry-run — print the plan (windows, symbol counts, artifact paths) and skip both the Databento materialize and the writes.
  • --allow-fetch — authorise the coverage resolver to submit a Databento Batch API job when the manifest cannot serve a request. Off by default; a MISS raises with a helpful message so accidental batch charges cannot happen from a stale end-date. Must be combined with --yes (or an interactive yes on a TTY) before any batch job is submitted.
  • --yes — non-interactive confirmation to proceed with fetches authorised by --allow-fetch. Batch API calls require BOTH --allow-fetch AND --yes (belt and braces). Without --yes a TTY prompt is offered; on a non-interactive terminal the run refuses and returns rc=10.

Exit codes

  • 0 — refit completed and artifacts were atomically written (or the --dry-run plan was printed).
  • 9 — coverage MISS on one or more schemas and --allow-fetch was not set; nothing was fetched, nothing was written.
  • 10 — coverage MISS with --allow-fetch set but the confirmation was refused (no --yes and no TTY, no at the prompt, or Ctrl-D / Ctrl-C). Nothing was fetched.

See “Cache-aware fetch guard” below for how the resolver decides HIT vs MISS and how the near-miss log names the closest parquet.

Cadence recommendation

  • Forecast and impact: weekly. The 12-month window ships along, and the imbalance signal’s regime does not sit still — a shorter refresh keeps the coefficients close to the current cross section.
  • Covariance: monthly. The factor structure is more stable and the 24-month window means each refit is a bigger Databento pull.

Run --refit all weekly and let the covariance be rebuilt over the same 24-month window each time if the batch cost is acceptable; otherwise split the schedule.

What each refit writes

Every write is staged to a .tmp file in the destination directory and then os.replaced into place — either the daily reads the previous version or the new one, never a torn file.

Cost note

The covariance refit does a materialize call on the ohlcv-1d schema over ALL_SYMBOLS for the full window. The first time you run it against a fresh cache this triggers a Databento batch job and consumes API budget; subsequent runs hit the parquet cache and are cheap. Use --covariance-window-days 30 for the very first smoke test.

Coupling with the daily

  • Feature engineering lives in live/features.py and is shared. Both scripts must agree on ALPHA_FEATURES order. If you change the feature set, retrain first, and only then let the daily pick up the new pipeline.
  • The optimizer indexes vectors positionally by the active universe. Changing the active-universe file requires rebuilding all three artifact sets in one pass, or the shapes will not line up and the daily will fail its shape checks before opening the feed.

7. Cache-aware fetch guard

Every historical read from retrain and daily_orchestrator --replay-date routes through the coverage manifest in live/cache.py before it can reach the Databento Batch API. This is the guardrail that turned “stale end-date silently triggers a paid fetch” into a coded refusal.

What the resolver does

  1. Fast path: try the adapter’s exact-hash parquet cache (data/dbn_cache/generic/<md5>.parquet). Hit → serve verbatim.
  2. Fall back to the coverage manifest, which fingerprints every parquet in data/dbn_cache/generic/ on schema, symbol set, and per-symbol date range. If an existing parquet’s contents cover the requested {schema, [start, end), symbols} slice, the resolver builds a filtered pl.LazyFrame off it — no new cache slot, no fetch. This is the “coverage HIT”.
  3. Otherwise MISS. The resolver refuses to fetch unless --allow-fetch was passed (and, for retrain, --yes too — see section 6). A refused MISS raises CoverageError with the nearest parquet, the shortfall, and the reason so the operator can diagnose without hand-inspecting the cache.

HIT criteria

  • Schema fingerprint matches (imbalance / tbbo / statistics / ohlcv-1d / ohlcv-1m / definition; ohlcv-1d vs 1m disambiguated on ts_event.time() cadence).
  • Parquet’s date range brackets the request window, floored to the nearest weekday (a parquet ending Friday covers a request whose exclusive end lands on Saturday or Sunday).
  • Every required symbol appears in the parquet AND its own per-symbol range brackets the request (guards against silent IPO / delisting false HITs).

Documented residual gaps

  • Exchange holidays are not modelled — a request whose closest weekday falls on a holiday not in the parquet will still false-MISS. A trading calendar is out of scope.
  • Interior-day gaps inside a parquet are not checked; only endpoints. Batch pulls are contiguous in practice, so this rarely bites — accept it as a known limitation.

Sidecar manifest

At data/dbn_cache/generic/.coverage_manifest.json, keyed on (mtime_ns, size_bytes) per parquet so a rewrite that preserves mtime still invalidates. Purely an optimisation — safe to delete; next run rebuilds it cheaply (one streaming group-by per parquet).

Flag summary

Command Flag Effect

retrain --yes Second gate for --allow-fetch. Non-interactive confirmation.
daily_orchestrator --replay-date --allow-fetch Authorise historical materialise on MISS. Single gate (cheap pull).
daily_orchestrator (live path) --allow-fetch Ignored — the live path uses the websocket feed, no historical cache.

9. Operational notes and troubleshooting

“Coverage assertion failed” (rc=2)

The snapshot covered less than --min-universe-coverage (default 0.5) of the active universe. Check, in this order:

  1. Did the live feed connect? Grep live feed started in the log. If missing, DATABENTO_API_KEY is wrong or the connection was refused.
  2. Grep snapshotted live feed — the n_imbalance_records and n_tbbo_records counts tell you whether the buffer was populated at all.
  3. If the buffer was populated but coverage was still thin, the universe file may have drifted from the SymbolMappingMsg output for this session (a ticker rename, a mis-typed symbol). The symbols_mapped count in feed_stats shows how many bindings were resolved.
  4. If you launched after 15:40, recent_return will have truncated — see section 5.

“past MOC submit cutoff” (rc=4)

The wall clock passed --submit-by before the orchestrator was ready to submit. Either the process started too late in the day, the MVO solve took longer than expected, or --print-wait-secs was set high enough to squeeze the submission window. The target book was persisted to live/logs/targets/YYYY-MM-DD.json before the cutoff check so you can see what would have been sent. Not applicable to replay. Distinct from rc=11, which fires after entries already filled — rc=4 is a safe pre-order skip, rc=11 is an active-exposure page.

“OVERNIGHT EXPOSURE” (rc=11)

Page immediately. Entries filled but the MOC exit did not fully cover the book. The ERROR log line names the concrete panic command and lists the uncovered / MOC-rejected symbols. Standard remediation:

# During regular hours — MKT flatten fills immediately.
.venv/bin/python -m live.panic --paper --flatten-with MKT
# Or the live variant:
.venv/bin/python -m live.panic --live \
  --live-confirm YES_I_WANT_LIVE_TRADING --yes

Common causes and where to look:

  • MOC exchange rejection — MOC batch fired 15:50:20+ or later, past the exchange entry cutoff. Grep MOC rejected at exchange in the log. Fix root cause by starting the run earlier (see section 5).
  • Uncovered symbols from a partial get_positions() snapshot — TWS event stream had a brownout during the MOC snapshot. Grep COVERAGE GAP / uncovered_symbols — the log names each missing symbol.
  • Stale non-terminal get_order_status — the cross-check saw a non-terminal read at cross-check time (should always be terminal after the MKT settles or the belt-and-braces cancel loop pulls it). Grep non-terminal status at cross-check time. Same TWS-brownout family as above.
  • MOC skipped past --submit-by — the MOC batch fired but only some legs made the cutoff. Grep legs skipped past submit cutoff. Widen the window between --rebalance-time + --print-wait-secs and --submit-by, or start earlier.
  • get_positions() raised entirely — TWS dropped between entry fills and the MOC snapshot. Grep get_positions FAILED. Panic then investigate the TWS logs.

After remediation, the next daily run’s _reconcile_from_previous will read the persisted target JSON at live/logs/targets/YYYY-MM-DD.json and flag any drift against the current positions.

“broker connect failed” (rc=8)

The most common causes:

  • Paper mode requested against a live TWS port (7496 / 4001). Broker._LIVE_PORTS refuses paper on those ports.
  • TWS not running, or running on a different port than expected.
  • Another orchestrator holding --broker-client-id 1; either wait or pass a distinct --broker-client-id.

Nothing has been placed at rc=8 — safe to fix and retry.

After an incident

  • live/logs/targets/YYYY-MM-DD.json — the intended book. Compare against broker.get_positions() to see what actually landed.
  • live/logs/fills/YYYY-MM-DD.jsonl — every order the audit heard back from. A missing order id means the order was never placed (check the main log for a leg submission failed or legs skipped entry).
  • On the next daily run, _reconcile_from_previous picks up yesterday’s target JSON and calls broker.reconcile_positions; any drift is logged as a warning at startup.

Do not

  • Run two orchestrators against the same TWS with the same --broker-client-id. TWS accepts the second connection but silently loses one of the two order streams.
  • Run panic against the same TWS client-id as an in-flight orchestrator run. Panic’s cancel_all() would pull the orchestrator’s own MKT entries and MOCs mid-flow, corrupting the rc gate. Panic defaults to client-id 99; orchestrator to 1. Keep them distinct. See the concurrency warning in section 10.
  • Run the retrain and the daily simultaneously against the same artifact directory during the writes. Retrain’s writes are atomic per file, but a run that spans a mid-write moment on a different file could read a mixed set (e.g. new loadings, old idio-diag). Schedule the retrain during off-hours.
  • Edit the .npy or .joblib artifacts by hand. Retrain them.
  • Follow a --replay-submit rehearsal with a real paper run without flattening the paper account. The replay fills sit there and will show up as drift in the next reconciliation.

Nonsense-book diagnosis

If the daily submits a book that looks wrong (odd GMV, wrong sign, concentrated in one name), check:

  1. coverage in the day_df built log entry — a thin snapshot with only a few names produces a degenerate cross section.
  2. retrain complete in the retrain log — confirm the last retrain actually finished and wrote atomically.
  3. live/logs/targets/YYYY-MM-DD.json — the exact numbers the orchestrator produced. Sanity-check gmv_dollar and vol_cap against your intent.
  4. The launch time — see section 5. A late launch silently truncates recent_return.

10. Panic — the kill switch

.venv/bin/python -m live.panic --help

live/panic.py is the account-wide kill switch: it connects to TWS, cancels every open order, and (unless --cancel-only) flattens every non-flat position via per-leg broker.close_position(sym, order_type=...). Deliberately small and blunt — this is what an operator runs when something is on fire.

Scope is ACCOUNT-WIDE, not universe-scoped. Unlike the daily orchestrator (which pins out-of-universe positions to their current qty and never touches manual trades), panic closes every non-flat position IB reports — including other-strategy books and manual trades on the same account. Operators of a shared account must know this before hitting the button.

CONCURRENCY WARNING — do NOT run panic against the same TWS client-id while an orchestrator run is in flight. Panic uses client-id 99 by default; the orchestrator uses 1. Distinct ids let them coexist against the same TWS but they must NEVER target the same client-id concurrently. Panic’s cancel_all() is a global cancel over the client’s orders — running it against the orchestrator’s client-id mid-flow would pull the orchestrator’s own MKT entries and MOC exits between submission and the acceptance / coverage audits, corrupting the rc gate and possibly leaving an open book unhedged. The two-leg model’s ordering guarantees only hold when it has exclusive control of its client-id for the duration of a run.

If a mid-flow panic is unavoidable, panic with client-id 99 (the default) — it operates on the account, not the orchestrator’s client — and let the orchestrator’s rc gate observe the resulting state naturally.

Two gotchas the script prints up-front:

  1. --flatten-with MOC after the exchange’s ~15:50 ET entry cutoff: the exchange typically rejects new MOC submissions past this cutoff and cancel_all() cannot pull already-accepted MOC orders. A late MOC panic may be a no-op.
  2. --flatten-with MKT outside regular trading hours (weekday 09:30–16:00 ET, holidays not modelled): MKT orders queue until the next open — they do NOT flatten immediately.

CLI reference

Mode:

  • --paper — paper mode. Default. Connects to TWS port 7497.
  • --live — live mode. Requires --live-confirm=YES_I_WANT_LIVE_TRADING and connects to port 7496. Also triggers an interactive PANIC prompt (skippable with --yes).
  • --live-confirm LIVE_CONFIRM — the broker confirmation string. Must be exactly YES_I_WANT_LIVE_TRADING — see ../CLAUDE.md.

Behaviour:

  • --flatten-with {MKT,MOC} — order type for the flatten. Default MKT. MKT fills immediately during regular hours; MOC fills at the 16:00 auction (clean end-of-day flatten) but is subject to the ~15:50 cutoff (see gotcha #1).
  • --cancel-only — cancel open orders but do NOT flatten positions.
  • --dry-run — connect, print the BEFORE snapshot, place nothing.
  • --yes — skip the interactive PANIC confirmation prompt (--live only prompts by default). Paper mode without --yes proceeds silently — this is the “quick oh-no” ergonomics.

Broker:

  • --broker-host BROKER_HOST — TWS host. Default 127.0.0.1.
  • --broker-port BROKER_PORT — TWS port. Default auto (7497 paper, 7496 live).
  • --broker-client-id BROKER_CLIENT_ID — TWS client id. Default 99 — distinct from the daily orchestrator’s default (1) so panic can connect while the daily is holding its own client id.

Golden commands

Inspect only — connect, print BEFORE snapshot, place nothing:

.venv/bin/python -m live.panic --paper --dry-run

The everyday panic — cancel every open order and MKT-flatten every non-flat position during regular trading hours:

.venv/bin/python -m live.panic --paper

Cancel-only variants (useful before a MOC panic near the close, or when you want to pull queued orders without flattening):

.venv/bin/python -m live.panic --paper --cancel-only
.venv/bin/python -m live.panic --paper --flatten-with MOC        # end-of-day clean flatten

Live counterparts (the confirmation string is required and the prompt is skippable with --yes for scripted use):

.venv/bin/python -m live.panic --live --live-confirm YES_I_WANT_LIVE_TRADING
.venv/bin/python -m live.panic --live --live-confirm YES_I_WANT_LIVE_TRADING --yes

Exit codes

  • 0 — clean. Cancel + flatten completed and the AFTER snapshot shows no lingering non-panic orders and (for the flatten path) no non-flat positions remain.
  • 1 — NOT FLAT / partial failure. Some combination of: lingering non-panic orders after cancel_all, per-leg flatten failures, positions still non-flat in the AFTER snapshot, MOC flatten submitted past the ~15:50 cutoff (likely rejected), OR the AFTER snapshot itself couldn’t be taken because TWS went unreachable (“COULD NOT CONFIRM FLAT”). Investigate the printed BEFORE / AFTER snapshots.
  • 2 — operator declined the live PANIC prompt.
  • 8 — broker connect failed. TWS not running, wrong port, or a --broker-client-id collision.
  • 9 — --live was requested without the exact --live-confirm string.

Post-panic verification

The AFTER snapshot is the source of truth, not the exit code. On a slow TWS, get_positions() can under-report. Eyeball the printed AFTER block: it lists every open order and every non-flat position. rc=0 combined with an AFTER snapshot showing 0 orders and 0 non-flat positions is the only genuine “flat” state.

Panic is intentionally a separate binary from the daily orchestrator so exit-code numbers don’t collide: daily_orchestrator uses 0/2/3/4/5/6/7/8/9/11, panic uses 0/1/2/8/9. A wrapper keying on the orchestrator’s rc numbers must not also key on panic’s — the same integer means different things across the two binaries.

.venv/bin/python -m pytest data_collection/tests/ live/tests/ -v

All 189+ tests should be green. The suite is fast (about two seconds). Safety-critical tests are grouped by module below — each one locks in a specific correctness or safety claim; if one goes red the corresponding guarantee is broken.

Test files that matter here:

  • live/tests/test_cache.py — coverage manifest + resolver (schema/date/symbol coverage, sidecar invalidation, HIT vs MISS, fetch-guard behaviour with and without --allow-fetch).
  • live/tests/test_retrain.py — atomic-write helpers + retrain’s --allow-fetch / --yes gating (rc=9, rc=10) + the coverage-plan log format regression (parquet name + reason must appear on MISS).
  • live/tests/test_replay.py — replay path end-to-end through daily_orchestrator (broker-free default, --replay-submit, guard-matrix rcs, per-leg cutoff neutralisation, tagged target book) + replay-side coverage-plan log format regression.

First-time smoke check

Before the first paper session, run the dry-run smoke to prove the whole pipeline is wired without touching the network or the broker:

.venv/bin/python -m live.daily_orchestrator \
  --dry-run --no-live-feed \
  --rebalance-time 00:00 --stream-start-time 00:00 \
  --submit-by 23:59 --on-feed-failure proceed

Expected in the log tail (stream handler goes to stderr): orchestrator starting, loaded active universe, loaded forecast pipeline, loaded covariance artifacts, MVO solved, share targets computed, empty share_targets — refusing to touch the broker (with rc=5), or in the --dry-run variant DRY RUN — printing target book. Any earlier exit means one of the prerequisites in section 2 is missing.

Second smoke: a broker-free replay of a date already in your historical cache — this proves the replay path end to end without live-imbalance airtime:

.venv/bin/python -m live.daily_orchestrator \
  --replay-date 2026-05-15 --paper

Expected: replay mode: starting historical feed, then the same MVO solved, share targets computed, target book persisted chain, then REPLAY (no-submit) — book computed and persisted... and rc=0. The persisted record lands at live/logs/targets/replay/2026-05-15.json.

12. Exit-code reference

Consolidated from sections 4 (daily), 6 (retrain), and 10 (panic). Panic is a separate binary from the daily orchestrator so rc numbers don’t collide with each other.

live.daily_orchestrator

Pager predicate: rc >= 11 is the ONLY code that implies a live book at close. Everything in [2, 10] is a safe pre-order refusal or clean shutdown.

rc Meaning
0 MVO solved; two-leg batch completed (or dry-run / broker-free replay summary). Cross-check clean, MOC acceptance audit clean.
2 Live feed / feature build failed (coverage assertion, LiveFeed.start() / ReplayFeed.start() exception, cold-cache replay without --allow-fetch).
3 MVO solver returned a non-optimal status.
4 Wall clock past --submit-by at submit time; NOTHING placed. Never fires in replay. Safe skip.
5 Target book was empty and --dry-run was not set. Broker not contacted.
6 --replay-date + --live was requested. Refused. No broker contact.
7 --replay-submit was requested without --replay-date. No broker contact.
8 Broker refused the connection (live-port guard, TWS down, --broker-client-id collision).
9 --lambda- <= 0 (invalid argument). No broker contact.
11 OVERNIGHT EXPOSURE — page. Entries filled but MOC exit did not fully cover: MOC legs skipped past cutoff, get_positions failed, stale-empty snapshot, cross-check found uncovered symbols (partial snapshot / budget-exhausted / TWS-brownout stale non-terminal), or MOC acceptance audit found exchange rejections. ERROR log names the concrete panic command and the uncovered / rejected symbols.

live.retrain

rc Meaning
0 Refit completed and artifacts atomically written (or --dry-run plan printed).
9 Coverage MISS on one or more schemas and --allow-fetch was not set. Nothing fetched.
10 Coverage MISS with --allow-fetch set but confirmation refused (no --yes / no TTY / no at prompt / Ctrl-D). Nothing fetched.

live.panic

rc Meaning
0 Clean. Cancel + flatten completed; AFTER snapshot shows no lingering non-panic orders and no non-flat positions.
1 NOT FLAT / partial failure: lingering orders, per-leg failures, positions remain, MOC past cutoff, or “COULD NOT CONFIRM FLAT” (TWS dropout during AFTER snapshot).
2 Operator declined the PANIC prompt (live mode).
8 Broker connect failed.
9 --live without the exact --live-confirm string.
